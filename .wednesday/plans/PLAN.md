## Overview

**Nyaya-Drishti** (Hindi: "Vision of Justice") is an administrative queue-triage system for district courts, built as a Smart India Hackathon (SIH) prototype.

The system identifies pending cases that are **structurally stalled** — not merely old — estimates the likely **administrative bottleneck**, and produces an **explainable priority score (0–100)** for court registry staff.

It does **not** predict judicial outcomes, evaluate judges, or access real case data. All case-level data is synthetic; real government aggregate statistics from NJDG/data.gov.in provide contextual grounding.

**The central demo moment**: two cases of similar age — one still progressing, one structurally stalled — placed side-by-side. Only the stalled one should rank at the top. The reason must be traceable to specific stored evidence.

## Triage Engine (6 Layers)

### Layer 1 — Cohort Builder
- Filters: `court_establishment` + `case_type` + `act_section_bucket` + `filing_year_bucket` + `current_stage`
- **`filing_year_bucket` definition (canonical, used everywhere):** `floor(filing_year / 2) * 2` — i.e., cases filed in 2019 or 2020 both map to bucket `"2018"` (floor of 2019÷2=1009, ×2=2018); cases filed in 2021 or 2022 map to `"2020"`. This is a fixed 2-year floor bucket. The seed generator, cohort builder, cohort endpoint, and triage engine must all use the **identical** Python expression `str((filing_year // 2) * 2)` — stored in `seed/config.py::cohort_year_bucket(year: int)` and imported everywhere.
- Minimum n = 15. Below threshold: `confidence = LOW`, percentile suppressed, warning shown in UI.
- **No judge identity in cohort keys. Ever.**

### Layer 2 — Stall Detector
Computes per case (using `is_substantive = True` events only):
- `days_since_substantive_event`
- `days_in_current_stage`
- `stage_deviation_ratio` = days_in_stage / cohort_median_days_in_stage
- `cohort_age_percentile`
- `adjournment_streak` (consecutive adjournments, no substantive event)
- Judge-change grace period: 60 days post judge-change → inactivity score × 0.5

### Layer 3 — Bottleneck Classifier (deterministic cascade)
```
1. SUMMONS_ISSUED + no SUMMONS_RETURNED within 90d → SUMMONS_DELAY
2. stage=Evidence + days_since_substantive > 180    → WITNESS_DELAY
3. adjournment_streak ≥ 4                           → REPEATED_ADJOURNMENT
4. judge_change_count ≥ 2 in last 365d             → JUDGE_CHANGE (UI: "Bench Change")
5. days_since_substantive > 120                     → PROCEDURAL_INACTIVITY
6. else                                             → UNKNOWN
```
Every case gets exactly one label. UNKNOWN is valid.

### Layer 4 — Scorer (0–100)

**Approved Phase 0 formula (locked):**

```
A (structural deviation) = min(stage_deviation_ratio / 5.0, 1.0) × 100  × 0.30
B (inactivity)           = min(days_since_substantive / 300, 1.0) × 100  × 0.25
C (age deviation)        = cohort_age_percentile                          × 0.15  [0 if LOW conf]
D (adjournment pattern)  = min(adjournment_streak / 5, 1.0) × 100        × 0.10
E (actionability)        = {LOW/UNKNOWN: 0, MEDIUM: 50, HIGH: 100}        × 0.20

triage_score = round(A + B + C + D + E, 1)   # already on 0–100 scale
```

Where `stage_deviation_ratio = days_in_current_stage / cohort_median_days_in_stage`
and `days_in_current_stage = (engine_run_date - Case.stage_entered_at).days`.
`stage_entered_at` is set from the latest `STAGE_TRANSITION` event for this case and is the **auditable provenance** for the structural deviation claim.

Weights stored in `triage/config.py` — never hardcoded inline.


### Layer 5 — Evidence Bundler
All 10+ fields stored as JSON in `cases.evidence_json`. Every field in the explanation text must appear in this bundle.

### Layer 6 — Explanation Templates
One template per (bottleneck_type × confidence) combination. Zero LLM involvement. Template renders explanation string from evidence bundle values.

> **UI Display Note**: `JUDGE_CHANGE` bottleneck label must render as **"Bench Change"** in all UI components — never "Judge Delay" or any wording implying judicial fault.

## Tensions

*Unresolved disagreements and design trade-offs between personas — documented explicitly for future decision-making.*

### T-1: Cohort minimum threshold (Architect vs. PM)
**Architect** recommends n ≥ 15 as the minimum for percentile confidence.
**PM** points out that in a 1,000-case single-court dataset with 3 act buckets and 5 filing years, some combinations will produce cohorts of 20–40, which is acceptable. However, if additional filtering is added (e.g., by stage), cohorts can fall below 15.
**Resolution for v1**: Use n ≥ 15. Pre-verify in seed generator that at minimum the demo case types have cohorts of ≥ 100. Flag LOW confidence in UI but do not suppress the case from the queue.

### T-2: JWT storage (Security vs. Developer Experience)
**Security** flags localStorage as XSS-exposed and recommends HttpOnly cookies for production.
**PM** notes that for a localhost SIH demo, localStorage is standard hackathon practice and saves 1–2 hours.
**Resolution for v1**: Use localStorage. Document the production upgrade path (`HttpOnly cookie + CSRF`) in `security.md` under FL-05. Do not implement for prototype.

### T-3: Timeline chart complexity (Architect vs. PM)
**Architect** specifies a Recharts ComposedChart with cohort median line and IQR band overlay (the "visually impressive" demo feature).
**PM** flags this as the highest-risk item for the 1-day timeline — custom Recharts compositions can take 2–3 hours to get right.
**Resolution**: Build the timeline as a **vertical event list first** (1 hour). Only upgrade to a Recharts chart if time allows. The evidence panel (score breakdown + explanation text) is the primary explainability proof; the chart is secondary.

### T-4: Seed data format — JSON vs. pre-built SQLite
**Architect** recommends committing `seed_data.json` (human-readable, diffable).
**PM** prefers committing the built `nyaya.db` directly (zero rebuild time for demo reset — critical at 2am in a hackathon).
**Resolution**: Commit both. Keep `seed_data.json` as the source of truth; provide a `seed/load_json.py` script that rebuilds `nyaya.db` from it in < 10 seconds.

### T-5: Single case type vs. multiple (PM vs. Architect)
**PM (Q&A)** chose single case type for deepest cohort coherence.
**Architect** notes this limits the demo's ability to show the system generalising across different legal domains.
**Resolution for v1**: Use Civil Suit (CS) as the primary type. Add 2 secondary case types (e.g., Criminal Case — CC, Execution Petition — EP) in the seed data with their own cohorts, but do not build separate UI views for them. The priority queue will naturally include all types.

### T-6: What "substantive event" means (all personas)
All three personas raised this as a definition risk — different definitions produce very different stall-detection outcomes.
**Resolution**: `is_substantive` is a boolean field on `case_events`. Default taxonomy:
```
HEARING         → is_substantive = True
ORDER           → is_substantive = True
WITNESS_EXAM    → is_substantive = True
SUMMONS_RETURNED→ is_substantive = True
ADJOURNMENT     → is_substantive = False
SUMMONS_ISSUED  → is_substantive = False
JUDGE_CHANGE    → is_substantive = False
```
This definition is stored in `seed/config.py` and is the single source of truth for both the seed generator and the triage engine.

## SIH Demo Script (90 seconds)

> **Act 1 — The Problem (15s)**
> "India's district courts have over 48 million pending cases. Every registry officer faces the same question: which case needs attention first?"

> **Act 2 — Why Age Alone Fails (15s)**
> "Sorting by age gives us two 5-year-old cases side by side. But they're not the same. One had a hearing three weeks ago. The other hasn't moved in nine months."

> **Act 3 — Nyaya-Drishti Triage (20s)**
> "Nyaya-Drishti scores each case against comparable cases — same court, same type, same era. It identifies structural stall, classifies the administrative bottleneck, and ranks the queue."

> **Act 4 — The Evidence (20s)**
> "Open the high-priority case. Every number is traceable to the court record. 287 days without a substantive hearing. A stage-deviation of 4.28× the cohort median — this case has been stuck in summons for more than four times longer than comparable cases. 5 consecutive administrative adjournments. The system classifies this as a Summons/Service Delay — the summons was issued 287 days ago with no service return on record. That is rule 1 of the bottleneck classifier. It fires before any other rule. That is why this case ranks first."

> **Act 5 — The Contrast (10s)**
> "The progressing case? Filed the same year. Heard three weeks ago. No adjournment streak. It scores low — computed by the same formula from its own cohort data — because it is moving normally."

> **Act 6 — The Boundary (10s)**
> "Nyaya-Drishti does not predict outcomes. It does not evaluate judges. It identifies where the administrative process has stalled — so registry staff can act."

## Secret / Credential Policy

| Environment | Missing JWT_SECRET | Missing ADMIN_PASSWORD / REGISTRY_PASSWORD | Behaviour |
|---|---|---|---|
| `APP_ENV=development` (default) | `warnings.warn` + dev fallback | `warnings.warn` + dev fallback | Server starts; warning visible in console |
| `APP_ENV=demo` | `RuntimeError` — **hard fail** | `RuntimeError` — **hard fail** | Server refuses to start |
| `APP_ENV=production` | `RuntimeError` — **hard fail** | `RuntimeError` — **hard fail** | Server refuses to start |

For the SIH demo: **set `APP_ENV=demo`** in `backend/.env` on the day of the presentation. This ensures that if the `.env` file is accidentally cleared or incomplete, the server will fail at startup rather than silently use a known-weak secret.

The `.env` file committed to the repo during prototype development **must contain** real values for all three variables before demo day.
