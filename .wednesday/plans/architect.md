## 1. System Design Overview

Nyaya-Drishti is a two-tier monolith for the prototype phase:

```
┌──────────────────────────────────────────────────────────┐
│  Frontend (React + Vite + Tailwind + Recharts)            │
│  Served on: localhost:5173 (dev) / static build (prod)   │
│                                                          │
│  Views: Dashboard | Priority Queue | Case Detail |       │
│         Comparison | Login                               │
└─────────────────────────┬────────────────────────────────┘
                          │ REST (JSON) + JWT Bearer
┌─────────────────────────▼────────────────────────────────┐
│  Backend API (FastAPI + uvicorn)                          │
│  Port: 8000                                              │
│                                                          │
│  Routers: /auth | /cases | /queue | /cohort | /stats    │
│                                                          │
│  Core modules:                                           │
│    triage/   ← stall detector, scorer, bottleneck class  │
│    data/     ← cohort builder, evidence bundler          │
│    seed/     ← synthetic data generator (run-once)       │
└─────────────────────────┬────────────────────────────────┘
                          │ SQLAlchemy
┌─────────────────────────▼────────────────────────────────┐
│  Database (SQLite — file: nyaya.db)                      │
│                                                          │
│  Tables: users | cases | case_events | triage_results   │
│          cohort_stats | aggregate_context               │
└──────────────────────────────────────────────────────────┘
```

**No microservices. No message queues. No external dependencies beyond the stack above.**

## 5. Triage Engine Design

### Layer 1 — Cohort Builder (`data/cohort_builder.py`)
```
Input:  case record
Output: filtered set of cases matching:
        - same court_establishment
        - same case_type
        - same act_section_bucket
        - same filing_year_bucket (±2 years)
        - same current_stage (for stage-aware stats)
        
Minimum n = 15. If cohort_size < 15:
  → confidence = LOW
  → suppress percentile component from score
  → emit cohort_warning = True
```

### Layer 2 — Stall Detector (`triage/stall_detector.py`)
```
Inputs: case events (is_substantive=True only), cohort_stats

Computes:
  days_since_substantive_event   (current date - last substantive event date)
  days_in_current_stage          (current date - stage-entry date)
  stage_deviation_ratio          (days_in_current_stage / cohort_median_days_in_stage)
  cohort_age_percentile          (case age vs cohort age distribution)
  adjournment_streak             (consecutive adjournments with no substantive event)
  
  Judge-change grace period:
    if judge_change_count > 0 and days_since_last_judge_change < 60:
      apply grace_factor = 0.5 to inactivity score component
```

### Layer 3 — Bottleneck Classifier (`triage/bottleneck.py`)
Deterministic rule cascade (evaluated in order):

```
1. If latest event = SUMMONS_ISSUED and no SUMMONS_RETURNED within 90d:
   → SUMMONS_DELAY

2. If current_stage = 'Evidence' and days_since_substantive > 180 and 
   last substantive event type ∈ {WITNESS_EXAM, HEARING}:
   → WITNESS_DELAY

3. If adjournment_streak ≥ 4 with no substantive event in between:
   → REPEATED_ADJOURNMENT

4. If judge_change_count ≥ 2 in last 365d:
   → JUDGE_CHANGE

5. If days_since_substantive > 120 (no other rule matched):
   → PROCEDURAL_INACTIVITY

6. Else:
   → UNKNOWN
```

The cascade ensures every case gets exactly one bottleneck label. UNKNOWN is valid and expected.

### Layer 4 — Scorer (`triage/scorer.py`)

```
Components (all normalised 0–1 before weighting):

  A. Inactivity score     = min(days_since_substantive / 365, 1.0)
  B. Age deviation score  = min(cohort_age_percentile / 100, 1.0)   [0 if LOW confidence]
  C. Stage deviation      = min(stage_deviation_ratio / 5.0, 1.0)
  D. Adjournment density  = min(adjournment_streak / 10, 1.0)
  E. Actionability bonus  = 0.1 if bottleneck ≠ UNKNOWN, else 0.0

Weights (v1 heuristic, configurable):
  A: 0.35
  B: 0.25
  C: 0.20
  D: 0.10
  E: 0.10

raw_score = A*0.35 + B*0.25 + C*0.20 + D*0.10 + E*0.10
triage_score = round(raw_score * 100, 1)   # 0.0 – 100.0
```

Weights are stored in `triage/config.py` as a named constant dict — they are NOT hardcoded inline, making calibration easy.

### Layer 5 — Evidence Bundler (`triage/evidence.py`)

### Layer 6 — Explanation Template (`triage/templates.py`)
```
Template for REPEATED_ADJOURNMENT + HIGH confidence:

"This case (filed {filing_date}) has been pending for {case_age_days} days.
It is at the {cohort_age_percentile}th percentile of age in its cohort 
of {cohort_size} comparable cases (median: {cohort_median_age_days} days).
The last substantive court event was {days_since_substantive_event} days ago.
The case has had {adjournment_count} adjournments, with {adjournment_streak} 
consecutive adjournments and no substantive progress.
Administrative review may help resolve the adjournment pattern.
[Score: {triage_score}/100 | Confidence: HIGH | Data: SYNTHETIC]"
```

One template per bottleneck type × confidence level combination.

## 6. API Design

### Auth
```
POST /auth/token          → {access_token, token_type, role}
POST /auth/refresh        → {access_token}
GET  /auth/me             → {username, role}
```

### Cases
```
GET  /cases               → paginated list (filters: status, stage, type)
GET  /cases/{id}          → full case record + evidence_json
GET  /cases/{id}/timeline → ordered case events
GET  /cases/{id}/cohort   → cohort stats for this case
```

### Queue
```
GET  /queue               → cases sorted by triage_score DESC
                            query params: limit, offset, bottleneck_filter, confidence_filter
```

### Stats
```
GET  /stats/aggregate     → NJDG aggregate context figures (data_label=REAL_AGGREGATE)
GET  /stats/summary       → synthetic dataset summary (data_label=SYNTHETIC)
```

### Demo
```
GET  /demo/comparison     → returns the 2 flagged demo cases (is_demo_stalled, is_demo_progressing)
```

## 7. Infrastructure and CI/CD

For prototype phase — minimal:
- **Local dev**: `uvicorn main:app --reload` + `npm run dev`
- **Seed run**: `python -m seed.generator` (run once, writes nyaya.db)
- **Demo reset**: `python -m seed.reset` (wipes + re-seeds)
- **No Docker required for prototype**

Post-prototype production path:
- Containerise with Dockerfile (backend) + nginx static (frontend)
- PostgreSQL migration: swap SQLite URL in `database.py`
- Deploy: Railway / Render / GCP Cloud Run

---

## 8. Scaling Strategy

v1 (prototype): Single SQLite, single process. Sufficient for demo.

v2 (production path):
- PostgreSQL (read replicas for queue queries)
- Triage engine runs as a scheduled batch job (not real-time)
- Frontend: CDN static hosting
- API: horizontal scaling behind nginx

## 9. Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Cohort too small (n<15) in demo | HIGH | MEDIUM | Pre-generate seed with guaranteed cohort sizes ≥20 for demo case types |
| Timeline chart too complex to finish in time | HIGH | HIGH | Build timeline as a simple vertical list first; upgrade to Recharts composition only if time allows |
| JWT+CORS integration friction | MEDIUM | MEDIUM | Use a tested FastAPI+React JWT template; allocate 1 hour explicitly |
| Synthetic data feels fake | MEDIUM | HIGH | Calibrate against real NJDG distributions; use fixed seed for reproducibility |
| Scope creep kills the MVP | HIGH | CRITICAL | Lock MVP scope before writing a single line of code; PM agent defines the cut list |
| Triage weights produce wrong demo result | LOW | HIGH | Pre-verify demo cases produce expected score ordering before demo |
