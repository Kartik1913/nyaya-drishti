## 1. Existing Solutions and Their Weaknesses

### NJDG (National Judicial Data Grid)
- **What it does**: Near-real-time aggregate dashboards — pendency counts, age-wise breakdowns, disposal rates, state/district/court-level summaries.
- **What it does NOT do**: It does not identify *which specific pending cases* are structurally stalled vs. still progressing. It answers "how many?" not "which ones, and why?".
- **Data access**: Web portal only; no public bulk API; interactive dashboards that must be read by a human.

### eCourts Portal / Mobile App
- **What it does**: Individual case status lookup (by case number / CNR), cause list access, order/judgment downloads.
- **What it does NOT do**: Bulk export of complete case event histories. There is no official public API for event-level timelines.
- **Legal constraint**: Section 43 IT Act 2000 prohibits unauthorized bulk automated extraction. CAPTCHAs and rate-limiting are intentional barriers.
- **Conclusion**: **No legitimate bulk event-level case history is available via eCourts for a prototype.** Synthetic data is the correct and ethically safe path.

### Third-party datasets (Dataful, Kaggle, AWS Open Data)
- Some researchers have published cleaned NJDG aggregate datasets (state/district/case-type/age-bucket pendency statistics) in CSV/Parquet format.
- These are *aggregate* statistics, not individual case histories.
- Legitimate use: calibrate synthetic case timelines to match known aggregate distributions.
- **Action**: Use these aggregate CSVs as contextual "real government data" shown in the dashboard's pendency overview section.

### Prior academic ML/AI work
- Most research uses **black-box models** (XGBoost, Random Forest, LSTM) for delay *prediction* (how long will this case take?).
- Explainability is typically retrofitted via SHAP/VIP plots — post-hoc, not native.
- None of the surveyed work focuses on **triage for administrative staff** — the "which case needs attention now?" framing is novel.
- Nyaya-Drishti's hybrid rule+statistics approach is **differentiated**: it is natively explainable, not retro-explained.

### SIH legal-tech patterns (2024)
- Judges value: working demo > complex architecture. A "finished-feeling" prototype beats a half-built sophisticated one.
- The 90-second demo rule: Pain Point → Aha Moment → Impact.
- Workflow management tools (case tracking, timeline analysis) are a recurring winning category.
- **Key differentiator SIH judges respond to**: showing real-world institutional feasibility, not just a demo.

## 3. Non-Obvious Domain Challenges

### 3a. Cohort minimum-size problem
- In a single-court-establishment dataset, narrow cohort slicing (court + case type + act bucket + filing-year bucket) can produce cohorts of <10 cases.
- Percentile calculations on n<10 are statistically unreliable.
- **Mitigation**: Define a minimum cohort threshold (e.g., n≥15). Below threshold: set `confidence = LOW`, suppress percentile score component, show explicit warning in UI.
- This must be an explicit design constraint — not an afterthought.

### 3b. "Meaningful activity" definition problem
- Days-since-last-event is only meaningful if "meaningful event" is defined.
- An administrative adjournment (e.g., "adjourned at request of both parties") may look like activity but is not substantive progress.
- **Mitigation**: Define an event taxonomy with a `is_substantive` boolean flag. Stall detection should use last-substantive-event, not last-any-event.

### 3c. Stage-time heterogeneity
- Cases in different procedural stages have wildly different "normal" durations. A case at "evidence stage" spends far longer than one at "arguments stage."
- Using global inactivity thresholds produces false positives.
- **Mitigation**: Cohort median should be computed *per stage*, not per case globally. This makes the system stage-aware.

### 3d. Judge-change events inflate inactivity
- When a judge changes, the incoming judge must read the record. This causes a burst of apparent inactivity that is a normal, non-actionable event.
- Treating judge-change as a stall indicator unfairly elevates priority on such cases.
- **Mitigation**: Track judge-change count as a separate field. Apply a grace period (e.g., 60 days post judge-change) before inactivity contributes to stall score.

### 3e. Synthetic data believability gap
- Poorly generated synthetic data (e.g., random uniform distributions) will be immediately obvious to domain experts reviewing the SIH demo.
- **Mitigation**: Calibrate synthetic case distributions against real NJDG aggregate statistics (case type proportions, age-bucket distributions, disposal rates). Use structured generation, not random generation.

### 3f. Solo 1-day time constraint
- The biggest risk is scope creep. Every optional feature is a threat to finishing the core triage engine.
- **Mitigation**: Cut scope ruthlessly. The 5 MVP features in BRIEF are non-negotiable. Everything else is cut until the MVP is working end-to-end.

## 5. Regulatory and Compliance Context

- **Data Privacy**: No real litigant PII in the prototype. Party names must be anonymised (e.g., "Party A", "Party B" or generated pseudonyms). CNR-like identifiers must be synthetic.
- **IT Act 2000 s.43**: Prohibits unauthorized bulk system access. Prototype must not scrape eCourts.
- **Judicial sensitivity**: Any system that appears to evaluate judge performance will be rejected by judicial stakeholders. All wording must be carefully reviewed — "administrative review priority" not "judicial inefficiency".
- **AI ethics**: The system must never claim to predict outcomes. Explanation templates must be reviewed for any language that could be construed as a judicial prediction.

## 7. Hidden Complexity (Things That Take 3× Longer Than Expected)

1. **Cohort statistics computation**: Percentile calculation across a filtered cohort sounds simple but requires careful null handling, minimum-n checks, and stage-aware grouping. Plan 2× the time you think.
2. **Evidence bundle generation**: Assembling all the evidence fields that justify a score and rendering them in a readable template takes iteration. This is the core explainability feature — do not underestimate it.
3. **Timeline chart**: Rendering a case event timeline horizontally (or as a Gantt-like chart) against a cohort "expected progression" band in Recharts requires custom composition. This is the visually impressive part of the demo — allocate real time.
4. **CORS + JWT integration**: First-time FastAPI+React JWT integration always takes 30–60 extra minutes due to CORS headers, token storage choices, and interceptor wiring.
5. **Synthetic data quality**: Making synthetic data "feel" realistic (right stage distributions, right adjournment patterns, coherent event sequences) takes careful scripting. Use a fixed seed for reproducibility.

## 8. Success Patterns from Best Products in This Space

- **Clarity over sophistication**: The best legal-tech demos show exactly one "aha" moment per view. Do not crowd the UI.
- **Audit trail as a feature**: Showing *why* a case received a score is as important as the score itself — make the evidence panel prominent.
- **Comparison as the demo core**: The strongest moment in the demo is the side-by-side contrast of an old-but-progressing case vs. an old-and-stalled case. Design the UI around this contrast.
- **Explicit "not a judicial prediction" disclaimer**: Make this visible in the UI, not buried in documentation. Judges will want to see that the team understands the boundary.
- **Real data context**: Even if all case-level data is synthetic, showing a real NJDG aggregate figure (e.g., "48 million pending cases nationally") anchors the problem in reality and immediately establishes relevance.
